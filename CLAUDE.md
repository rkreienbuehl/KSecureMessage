# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

KSecureMessage is an early-stage Kotlin Multiplatform scaffold for a Signal-style secure messaging library built on [Kodium](https://github.com/LivotovLabs/kodium) (which provides the X3DH and Double Ratchet primitives). It adds the messaging lifecycle and infrastructure around those primitives. It does **not** aim for wire compatibility with Signal/libsignal. `KodiumProtocolEngine` implements milestone 1 (X3DH session setup, Double Ratchet, session export/restore; tests in `core/protocol/src/commonTest`). Milestone 2 added `CiphertextMessageCodec` (versioned binary wire format for `EncryptedEnvelope.payload`, spec in `docs/wire-format.md`) and the `SecureMessageClient` send/receive path; tests in `core/protocol` and `client/core` `commonTest`. Milestone 3 added client-owned identity/prekey lifecycle (`SecureMessageClient.initialize()`, `PreKeyManager`), atomic `ClientStorage.transaction` and the `storage:client:sqldelight` adapter; spec in `docs/storage.md`. Milestone 4 added prekey publication: `SecureMessageClient.publishPreKeys()`, the server `PreKeyRepository`/`PreKeyService` with atomic single-use one-time prekey handout, and HTTP API v1; spec in `docs/prekey-publication.md`, tests in `storage:server:inmemory`, `server:core`, `server:ktor` and `client:core`. Milestone 5 added remote identity trust on first use (`ClientStorage.remoteIdentities`, `SecureMessageClientException.IdentityChanged`, SQLDelight schema v2 via `1.sqm`); spec in `docs/identity-trust.md`, tests mainly in `client:core` `RemoteIdentityTrustTest`. Milestone 6 added session replacement, simultaneous-initiation resolution and replay protection on wire v1 (`SessionInitiationId`, session state format v2, `ClientStorage.sessionInitiations`, SQLDelight schema v3 via `2.sqm`); spec in `docs/session-lifecycle.md`, tests in `client:core` `SessionLifecycleTest`/`SessionReplacementAtomicityTest`. A milestone 6 follow-up made delivery order explicit: per (sender, recipient) FIFO via `SecureMessageClient.send`'s mutex and the `MailboxRepository` contract (`MailboxRepositoryContractTest` in `storage:testing`); spec in `docs/transport-ordering.md`, tests in `client:core` `SessionReorderingTest`. Milestone 7 added the signed prekey lifecycle: rotation by age, grace period, expiry and deletion, pruning of retired initiations tied to a deleted signed prekey, an injectable `kotlin.time.Clock`, session state format v3 (`acceptedSignedPreKeyId`) and SQLDelight schema v4 via `3.sqm`; spec in `docs/signed-prekey-lifecycle.md`, tests in `client:core` `SignedPreKeyLifecycleTest` and `storage:client:sqldelight` `SqlDelightPersistenceTest`. Milestone 8 added message reliability: `LogicalMessageId` (not the envelope `MessageId`), the encrypted `SecurePayloadCodec` frame v1 (`core:protocol`), pending outbound messages and processed inbound IDs in `ClientStorage`, encrypted ACKs, `retryPendingMessages`, public `send`/`decrypt` returning `SentMessage`/`ReceiveResult`, SQLDelight schema v5 via `4.sqm`; spec in `docs/message-reliability.md`, tests in `core:protocol` `SecurePayloadCodecTest`, `client:core` `MessageReliabilityTest`/`MessageCollisionRecoveryTest`/`MessageReliabilityAtomicityTest`, `storage:client:sqldelight` `SqlDelightPersistenceTest`. Milestone 9 added record-level client storage encryption: the `storage:encryption` module (AES-256-GCM via cryptography-kotlin, `ClientRecordCipher`, `StorageKeyProvider`, record format v1), `SqlDelightClientStorage.open(driver, keyProvider)` (no plaintext mode), SQLDelight schema v6 via `5.sqm` plus the Kotlin `LegacyPlaintextMigration`; spec in `docs/storage-encryption.md`, tests in `storage:encryption` `StorageCipherTest`/`ClientRecordCipherTest` and `storage:client:sqldelight` `SqlDelightEncryptionTest`/`SqlDelightMigrationTest`. Milestone 10 added platform storage key providers: `storage:keyprovider:android` (`AndroidStorageKeyProvider`, storage key wrapped by an Android Keystore AES-GCM key, wrapped key file format v1 in `noBackupFilesDir`) and `storage:keyprovider:apple` (`AppleStorageKeyProvider`, Keychain generic password item; macOS-only `legacyFileKeychain`); spec in `docs/storage-key-providers.md`, contract `StorageKeyProviderContractTest` in `storage:testing`, tests in both provider modules and `storage:client:sqldelight` `PlatformKeyProviderStorageTest` (Android subclass instrumented, Apple subclasses in `appleTest`/`macosTest`). Milestone 10.1 added the signed keychain host (`apple-keychain-host/`: `run.sh`, entitlements, the `keychain-host.gradle.kts` script plugin applied by both Apple-tested modules) that runs the `*DataProtection*` tests against the real data protection keychain; spec in `docs/storage-key-providers.md` ("Signed keychain host"). Milestone 11 added explicit storage key rotation and safe retirement: `SqlDelightClientStorage.rotateStorageKey()` / `resumeStorageKeyRotation(maxRecords)` / `storageKeyRotationStatus()`, rotation state in `storage_encryption` (SQLDelight schema v7 via `6.sqm`, frozen fixture `Version6Schema`), multi-key `ClientRecordCipher(current, vararg retained)`, `SealedRecords` header inspection, `StorageKeyProvider.createKey`/`removeKey`; spec in `docs/storage-key-rotation.md`, tests in `storage:client:sqldelight` `StorageKeyRotationTest`/`SqlDelightMigrationTest`/`PlatformKeyProviderStorageTest`/`MemoryStorageKeyProviderContractTest`, the extended `StorageKeyProviderContractTest` and `storage:encryption` `StorageCipherTest`. A post-M11 refactor moved the rotation state machine into `storage:rotation:core` (`StorageKeyRotationManager`, `StorageKeyRotationBackend`, `StorageKeyRotationState`, phase/status/in-progress exception in package `...storage.rotation`); `SqlDelightStorageKeyRotationBackend` implements it, behavior and formats unchanged; tests in `storage:rotation:core` `StorageKeyRotationManagerTest`/`StorageKeyRotationStateTest` (fake backend + recording provider). Milestone 12 added authenticated server API and device ownership: a dedicated Ed25519 device authentication key (`DeviceAuthenticationKeyPair`, `ProtocolEngine.createDeviceAuthenticationKey`, `ClientStorage.deviceAuthentication`, sealed record type 7, SQLDelight schema v8 via `7.sqm` with the `awaits_upgrade_key` marker, frozen fixture `Version7Schema`), explicit `SecureMessageClient.registerDevice()` (trust on first registration, proof of possession), signed requests (`ServerRequestAuthentication`, `ServerApiPaths`, `RequestNonce` in `core:protocol`; `DeviceAuthenticator`, `ProtectedEndpoint`, `AuthenticatedDevice` in `server:core`; `DeviceRegistrationRepository`/`AuthenticationNonceRepository` in `storage:core`) for prekey publication and mailbox drain (`SecureMessageClient.receive()`); spec in `docs/server-authentication.md`, tests in `core:protocol` `ServerRequestAuthenticationTest` (frozen vectors), `server:core` `DeviceAuthenticationServerTest`, `server:ktor` `AuthenticatedRoutesTest`/`HttpEndToEndTest`, `client:core` `DeviceAuthenticationTest`, `storage:client:sqldelight` `DeviceAuthenticationStorageTest`, `storage:server:inmemory` registration/nonce contract tests. A pre-M13 refactor split the storage adapters by side (structure and packages only, no behavior, schema or format change): `storage:client:inmemory` (`InMemoryClientStorage`, package `...storage.client.inmemory`), `storage:client:sqldelight` (`SqlDelightClientStorage`, rotation backend, package `...storage.client.sqldelight`, generated `...storage.client.sqldelight.db`) and `storage:server:inmemory` (`InMemoryServerStorage`, package `...storage.server.inmemory`); Milestone 13 added persistent server storage: `storage:server:sqldelight` (JVM only, package `...storage.server.sqldelight`, `SqlDelightServerStorage.open(driver)` on a host-owned SQLite `SqlDriver`, server schema v1 in `ServerState.sq` independent of the client schema) and generic `500 internal_error` for unexpected failures in the Ktor routes; spec in `docs/server-storage.md`, tests in `storage:server:sqldelight` (`SqlDelight*RepositoryTest`/`FileBacked*RepositoryTest` contract subclasses, `SqlDelightServerPersistenceTest`, `SqlDelightServerRollbackTest`, `SqlDelightServerStorageOpenTest`) and `server:ktor` `SqlDelightHttpEndToEndTest`. The README's "Next implementation steps" section is the roadmap.

## Commands

The Gradle wrapper (Gradle 9.6) is checked in. Tests exist in `core:protocol`, `client:core`, `storage:encryption`, `storage:rotation:core`, `storage:client:inmemory`, `storage:client:sqldelight`, `storage:server:inmemory`, `storage:server:sqldelight`, `storage:keyprovider:android`, `storage:keyprovider:apple`, `server:core` and `server:ktor`. There is no lint setup.

```bash
./gradlew build                          # everything (all KMP targets; native/iOS need macOS)
./gradlew compileKotlinJvm               # fast check of KMP modules via JVM target
./gradlew compileAndroidMain             # Android target of all client-side modules
./gradlew :server:core:compileKotlin :server:ktor:compileKotlin
./gradlew :core:protocol:jvmTest         # KMP module tests on JVM
./gradlew :core:protocol:macosArm64Test  # same tests, native
./gradlew :core:protocol:jvmTest --tests "dev.kreienbuehl.ksecuremessage.protocol.SomeTest"
./gradlew :server:core:test :server:ktor:test  # JVM-only modules use plain `test`
./gradlew :storage:server:sqldelight:test      # persistent server storage (JVM only, in-memory + file-backed SQLite)
./gradlew :storage:client:sqldelight:jvmTest :storage:client:sqldelight:macosArm64Test  # SQLite-backed tests (no JS/Wasm tests)
./gradlew :storage:rotation:core:jvmTest                       # storage key rotation state machine, fake backend
./gradlew :storage:keyprovider:android:testAndroidHostTest     # wrapped key file codec, JVM host
./gradlew :storage:keyprovider:android:connectedAndroidDeviceTest :storage:client:sqldelight:connectedAndroidDeviceTest  # needs a running emulator/device
./gradlew :storage:keyprovider:apple:macosArm64Test            # legacy keychain contract, no-fallback tests
./gradlew appleKeychainHostTest                                # data protection keychain in the signed host (macosArm64 + iosSimulatorArm64)
./gradlew iosSimulatorArm64KeychainHostTest                    # needs a booted simulator only
```

Instrumented tests (`connectedAndroidDeviceTest`) and the keychain host tasks are not part of `build`. Kotlin/Native test binaries are unsigned (macOS data protection keychain: -34018; iOS simulator runner: no keychain, -25291), so plain `macos*Test`/`ios*Test` tasks exclude every `*DataProtection*` test class; those run only in the host (`<target>KeychainHostTest`), which reports PASSED / FAILED / NOT EXECUTED. Never add a skip path that returns normally: a `DataProtection` test must fail when the keychain is unusable. macOS host signing comes from local `ksm.apple.teamId` / `ksm.apple.macosProfile` (never commit team IDs, identities or profiles). Host tasks share one lock (the simulator hosts share a bundle ID). `:storage:keyprovider:apple:<target>KeychainHostPurge` removes items an interrupted run left.

JS/Wasm test tasks (and so plain `./gradlew build`) fail with "repository 'Distributions at https://nodejs.org/dist' was added by unknown code". The cause is `RepositoriesMode.FAIL_ON_PROJECT_REPOS` in `settings.gradle.kts`. Until that is fixed, run `./gradlew build -x jsTest -x jsNodeTest -x jsBrowserTest -x wasmJsTest -x wasmJsNodeTest -x wasmJsBrowserTest`.

Configuration cache is on (`gradle.properties`). Android builds need `ANDROID_HOME` (a local SDK).

## Module layout and targets

- **Client-side / shared** (`core:model`, `core:protocol`, `storage:core`, `storage:encryption`, `storage:rotation:core`, `storage:client:inmemory`, `storage:client:sqldelight`, `storage:server:inmemory`, `storage:testing`, `client:core`, `client:ktor`): Kotlin Multiplatform with jvm, android, js, wasmJs, iOS, macOS, linuxX64, mingwX64. Exceptions: `storage:keyprovider:android` has only the android target (`androidMain`, `androidHostTest`, `androidDeviceTest`), `storage:keyprovider:apple` only iOS/macOS (`appleMain`, `macosMain`, `appleTest`, `macosTest`). Sources live in `src/commonMain/kotlin`. Android uses the AGP 9 `com.android.kotlin.multiplatform.library` plugin with a `kotlin { android { namespace/compileSdk/minSdk } }` block. The SDK levels come from `libs.versions.toml`.
- **Server** (`server:core`, `server:ktor`, `storage:server:sqldelight`): plain `kotlin.jvm` with `jvmToolchain(17)`. Sources live in `src/main/kotlin`. Do not add non-JVM targets here. The root `build.gradle.kts` sets the KMP JVM targets to Java 17 bytecode so the server can load them.
- `kotlin.mpp.applyDefaultHierarchyTemplate=false` is set, so there are no intermediate source sets (for example, no `iosMain`/`nativeMain`) unless you declare them explicitly.
- Each module's Maven group includes its parent directory (`dev.kreienbuehl.ksecuremessage.client:core`, `...storage:core`), set in the root `build.gradle.kts`. Several modules are named `core`. With a shared group, Gradle resolves `:storage:core` to itself and reports circular task dependencies, so keep coordinates unique.
- Dependency versions live only in `gradle/libs.versions.toml`.
- `storage:client:sqldelight` and `storage:keyprovider:apple` link `apple-keychain-host/ios-simulator.entitlements` into their `iosSimulatorArm64` test binaries (`-sectcreate __TEXT __entitlements`). `storage:client:sqldelight` wires custom test source sets: `sqliteTest` (shared by `jvmTest`, `nativeTest` and `androidDeviceTest`; `appleTest`/`macosTest` sit between `nativeTest` and the Apple targets), with `expect`/`actual` test drivers. JS/Wasm have no test sources there. Its linuxX64/mingwX64 test link and run tasks are skipped unless the host OS matches (they need the target's libsqlite3).
- `storage:testing` holds `ClientStorageContractTest`, `PreKeyRepositoryContractTest`, `MailboxRepositoryContractTest`, `DeviceRegistrationRepositoryContractTest`, `AuthenticationNonceRepositoryContractTest` and `StorageKeyProviderContractTest` (in `commonMain`, depends on kotlin-test). Every `ClientStorage` / server repository / platform `StorageKeyProvider` adapter's tests extend them.

## Architecture

Dependency direction: `core:model` ← `core:protocol` ← `storage:core` ← {`client:core`, `server:core`, `storage:client:inmemory`, `storage:server:inmemory`, `storage:server:sqldelight`, `storage:encryption` ← {`storage:rotation:core` ← `storage:client:sqldelight`, `storage:keyprovider:android`, `storage:keyprovider:apple`}}. `storage:client:*` = local client persistence, `storage:server:*` = server repository persistence, `storage:core` = the shared contracts (never duplicate them in an adapter module); `storage:encryption`, `storage:keyprovider:*` and `storage:rotation:core` are storage security infrastructure that today serves only persistent client storage. Main scopes never cross sides: no client module depends on a `storage:server:*` adapter and no server module on a `storage:client:*` adapter (only test scopes do: `client:core` tests use `InMemoryServerStorage` as fake server, `server:ktor` tests run a real client with `InMemoryClientStorage`). `storage:rotation:core` must never depend on SQLDelight or a platform module. `client:core` never depends on a storage adapter; applications choose one. The transport adapters (`client:ktor`, `server:ktor`) sit on top of those. `storage:core` depends on `core:protocol` because `SessionStore` persists `SecureSession`.

Key boundaries:

- **Kodium stays behind `ProtocolEngine`** (`core:protocol`). Public models use `ByteArray` for keys (`PreKeyBundle`) and ratchet state (`SecureSession.state`, meant to be Kodium's export/import blob). Do not leak Kodium types into model, storage, client, or server APIs. `kodium` is an `implementation` dependency on purpose.
- **Ratchet state must update atomically.** `ProtocolEngine.encrypt/decrypt` return an `updatedSession`. The client must persist it inside `ClientStorage.transaction { }` together with the crypto operation (see `SecureMessageClient`).
- **Server authentication (M12):** the device authentication key (Ed25519, 32-byte public key, 32-byte seed) is not the messaging identity key; never reuse or derive one from the other. Keys come only from `ProtocolEngine`; `initialize()` creates it with the identity, or once when `awaitsUpgradeKey()` (pre-M12 storage), and otherwise fails closed with `InconsistentStorage`; never regenerate a lost key. `initialize()` never registers; registration is explicit and verified with the key in its body (the only such endpoint); every other protected request verifies with the **registered** key, never one the request supplies. The signed input format v1 (domain `KSecureMessage-ServerAuth-v1`, vectors in `ServerRequestAuthenticationTest`) is frozen; sign the exact body bytes, never re-serialized JSON; paths come from `ServerApiPaths`, never the raw URI. Check order: present → registered → window (±5 min inclusive, injected `Clock`) → signature → nonce claim (atomic, per device, pruned by timestamp); authenticate before parsing or mutating. Protected operations need an `AuthenticatedDevice` (internal constructor). A registration is never replaced. Bundle fetch and `POST /v1/messages` stay public.
- **Server is a blind relay.** `SecureMessageServer` only stores public prekeys and queues opaque `EncryptedEnvelope`s per recipient `DeviceAddress` (`drain` removes the envelopes it returns). It must never decrypt payloads or hold client session secrets.
- **Server prekeys:** `PreKeyRepository` (`storage:core`) keeps per device an identity key, the current signed prekey, available one-time prekeys and consumed-ID tombstones. `publish` is atomic and idempotent; conflicts throw `PreKeyPublicationException` and change nothing. `consumePreKeyBundle` removes and tombstones the lowest-ID one-time prekey in one atomic step, so no one-time prekey is handed out twice, even if the client uploads it again. Server consumption is not client consumption: the client deletes its private one-time prekey only when it accepts the `PreKeyMessage`. `PreKeyFormat` (`core:protocol`) checks publication sizes without Kodium.
- **Message reliability (M8):** two layers in `SecureMessageClient`. Public = reliability layer (`send`, `decrypt`, `retryPendingMessages`, `pendingMessages`); `internal` `encryptRaw`/`sendRaw`/`decryptRaw` = session layer with M1–M7 semantics, used by it and by the M1–M7 tests (tests of session behavior use the raw layer; other modules' tests must use the public API and expect ACK envelopes in mailboxes). Every ratchet plaintext is a `SecurePayloadCodec` frame; no fallback for raw plaintext, never use `EncryptedEnvelope.protocolVersion` to detect it; frame v1 vectors are frozen. `send`: pending store + encryption + session in one transaction, hand-off after; `MessageNotSent` after a failed hand-off, never rewind the session. Pending is removed only by an ACK from that recipient, never on transport success. `decrypt`: processed marker in the receive transaction; ACK after the commit on the existing session only, under `sendMutex`, failures give `ackSent = false` (rethrow `CancellationException`); never ACK an ACK or anything that failed (collision, stale, identity, expired SPK, malformed frame). Retry re-encrypts the stored frame fresh, same logical ID, new envelope ID, in sequence order, stops at the first hand-off failure. Pending frames are **plaintext at rest**; processed IDs are never pruned.
- **Wire format:** `CiphertextMessageCodec` (`core:protocol`, no Kodium imports) owns the payload bytes; version-1 vectors in `CiphertextMessageCodecTest` are frozen. `EncryptedEnvelope.protocolVersion` versions only the envelope metadata. Protocol info strings live in `ProtocolConstants` and must never change.
- **Client storage:** `ClientStorage` has `identity`, `remoteIdentities` (TOFU pins), `sessions`, `sessionInitiations` (retired initiation IDs, each with an optional local signed prekey ID for pruning), `preKeys` (local private prekeys plus signed prekey `createdAt`/`replacedAt`), `pendingOutbound` (recipient + logical ID → never-reused sequence + encoded frame) and `processedInbound` (sender + logical ID). `transaction` must be atomic (rollback on throw), nested calls join the running transaction, and blocks must not do network I/O or switch threads. Accepting a `PreKeyMessage`, storing the session and removing the consumed one-time prekey happen in one `transaction`.
- **Local key lifecycle:** keys are created only by `ProtocolEngine`, never by storage. `PreKeyManager` allocates prekey IDs from persisted high-water marks (never reused, no wraparound; `PreKeyIdsExhausted`). Operations before `initialize()` throw `SecureMessageClientException.NotInitialized`. An existing identity is never replaced.
- **Signed prekey lifecycle (M7):** current → (rotate) grace → (grace over) physically deleted. Never delete at rotation. `initialize()` does all maintenance in one transaction (stamp pre-M7 keys, age rotation, expiry, pruning); it never publishes. Acceptance refuses a key past its grace period even before deletion (`ExpiredSignedPreKey`); never-issued IDs stay `InvalidMessage`. Negative ages are never due; deleted keys never come back. Only use the injected `Clock`, never `Clock.System` directly. Prune a retired initiation only by its **local** signed prekey ID and only after that key is deleted; `null` entries (own initiations, pre-M7) are kept. Established sessions never depend on the signed prekey.
- **Session lifecycle (M6):** every session stores the `SessionInitiationId` that created it (SHA-256, domain `KSecureMessage-SessionInitiation-v1`; vectors in `SessionInitiationIdTest` are frozen). A `PreKeyMessage` goes through `SecureMessageClient.receivePreKeyMessage`: identity check → same initiation (decrypt) → retired (`StaleSessionInitiation`) → accept, collision (smaller ID wins, the loser is authenticated, retired, `SessionCollision`, OTPK kept) or replacement (session + retire old origin + OTPK removal in one transaction). Header fields are authenticated only by `acceptSession`; never record an origin from `decrypt`. Sessions without a pin are never replaced. Never order initiations by "age": the ID order is only a tie-break.
- **Remote identity trust (TOFU):** pins are per `DeviceAddress`, written only after the protocol accepted the key (`initiateSession` / successful decrypt) and in the same transaction as the session (and OTPK removal). Check before crypto, pin after. A pin is never replaced; a different key throws `IdentityChanged` and changes nothing. No reset/accept API yet. Never derive a pin from the envelope sender address. SQLDelight schema changes need a new `.sqm` migration (current version 8) and a frozen schema fixture (`Version1Schema` … `Version7Schema`) for migration tests. A change to a sealed table also needs a Kotlin data migration like `LegacyPlaintextMigration`, because SQL cannot encrypt.
- **Storage encryption (M9):** `SqlDelightClientStorage` seals key pairs (whole identity/device-auth/SPK/OTPK records; device authentication key = record type 7, M12), session state and pending frames with `ClientRecordCipher` (`storage:encryption`); adapters never do crypto, AD or formats themselves. Only `AesGcm.kt` imports cryptography-kotlin; Kodium is not used for storage. AD = record header + domain `KSecureMessage-Storage-v1` + record type ID + length-prefixed row key fields; record type IDs, domain and record format v1 (vector in `StorageCipherTest`) are frozen. Nonces are always fresh random 96-bit. A record that fails to open throws `StorageEncryptionException`, never returns `null`; existence checks (identity already stored, pending duplicate) must not open records. No plaintext mode, no trial decryption: the `storage_encryption.format` row is authoritative (0 = M8 plaintext, migrated by `open` in one transaction; 1 = encrypted). Key providers are called outside transactions; `open` never creates a key for a database with a bound key. It is record-level encryption, not database encryption: metadata, row deletion and rollback are unprotected, and pre-M9 plaintext may remain in SQLite pages. `InMemoryClientStorage` does not encrypt. The pre-v6 sealed-table DDL exists twice (`ClientState.sq`, `LegacyPlaintextMigration.kt`; tables added later, like `device_authentication_key`, only in `ClientState.sq` and their `.sqm`); `SqlDelightMigrationTest.migratedSchemaEqualsNewSchema` checks they match.
- **Platform key providers (M10):** they only persist the unchanged 32-byte M9 key (`StorageEncryptionKey.generate`), never derive it. Create only when the provider has **no state**; state present but unreadable (missing Keystore alias, damaged file/item, wrong size, any OSStatus except not-found) is `KeyUnavailable`, never a new key, and never overwrites anything. Return a created key only after it was persisted and read back. `key(id)` never creates; `loadOrCreateKey()` refuses a namespace with several keys. `createKey(id)` returns an existing key unchanged or creates, persists and reads back a new one (needs a provisioned provider); `removeKey(id)` removes exactly one key and never the last one. No reset or delete-all API in production code; tests clean up with test-only helpers and random namespaces. Android: raw key never written; alias, file name, file format v1 and wrap AD are documented and frozen; files go through temp file + `ATOMIC_MOVE`; process mutex + file lock. Apple: item data is exactly the 32 raw bytes; service/account naming, `AfterFirstUnlockThisDeviceOnly`, non-synchronizable and data protection keychain are the defaults; never fall back to the legacy macOS keychain automatically. First key ID is 1.
- **Storage key rotation (M11):** not signed prekey rotation. The state machine (step order, allocation rule, provider calls and read-back, zero-reference rule, `removeKey == false` accepted only in RETIRING) lives only in `StorageKeyRotationManager` (`storage:rotation:core`); never duplicate phase logic in a backend. A backend (`SqlDelightStorageKeyRotationBackend`) owns persistence, transactions, phase encoding, key checks, batches and the scan; each transition is one atomic compare-and-set, and `markRetiring` runs the scan and the manager's check in the committing transaction. Generic state validation is `StorageKeyRotationState.of`. The database owns rotation state (`storage_encryption`: `key_id` current, `highest_key_id`, `rotation_phase` 0 STABLE / 1 PREPARING / 2 MIGRATING / 3 RETIRING, `next_key_id`, `retiring_key_id`, `retiring_key_check`); providers only hold keys; key IDs come from the high-water mark, never reused, no wraparound (`KeyIdsExhausted`). Order: allocate ID (commit) → `createKey` + read back → activate (commit) → batches → proof tx (clear retiring check, scan) → re-scan → `removeKey` → STABLE. Never let the database name a key before the provider persisted it; never remove a key before the scan committed RETIRING; `removeKey` returning `false` is fine only in RETIRING. New records always use the current key; reads pick the key by record header. Re-encryption `UPDATE`s only the sealed column, same AD, fresh nonce; one transaction per batch, failures roll back only that batch and keep MIGRATING. `SEALED_COLUMNS` must list every sealed column (checked against the schema by `sealedColumnsCoverEverySealedValueInTheSchema`). `open` loads exactly the keys the phase needs, verifies each key check with a single-key cipher, never advances or rolls back a rotation. Every top-level transaction checks the key state (stale instance → `KeyUnavailable`). No scheduler; orphan provider keys are never deleted.
- **Delivery order:** convergence needs, per (sender, recipient) pair, every `PreKeyMessage` processed before later envelopes of that sender (`docs/transport-ordering.md`). Keep every encrypt+hand-off (`send`, retries, ACKs) under `sendMutex` (never inside a storage transaction), and any `MailboxRepository` per-pair FIFO and exactly-once per drain. Order across senders is not promised; do not add sequence numbers to `EncryptedEnvelope`.
- **Persistent server storage (M13):** `SqlDelightServerStorage` takes a caller-supplied `SqlDriver`; never create, configure or close a driver in the adapter, and never expose a concrete driver type. SQLite dialect and synchronous drivers only; never claim other databases (a PostgreSQL adapter would be its own module). Main scope depends only on `storage:core` + SQLDelight runtime (never client storage, encryption, key providers or rotation). Every repository call is one transaction under the instance mutex; one instance per database. Never `INSERT OR REPLACE`; uniqueness lives in primary keys. The nonce claim (prune + insert) is its own transaction, never joined with the protected operation. Publication, OTPK hand-out (delete + tombstone) and drain (select + delete) are each one transaction; `enqueue` returns after commit. `mailbox_message.sequence` is `AUTOINCREMENT` (never reused). Schema changes need a server-own `.sqm` (no client numbering). `server:ktor` main never depends on SQLDelight (tests may). Restart tests must close the driver and reopen the same file.
- **HTTP contract** (API v1) is defined twice and must stay in sync: `client:ktor` (`KtorSecureMessageTransport`, `HttpDtos.kt`, `AuthHeaders`) and `server:ktor` (`KSecureMessageRoutes`, `HttpDtos.kt`, `AuthHeaders`); `server:ktor` tests run the client adapter against the routes. Routes: `PUT /v1/devices/{user}/{device}/registration` (signed), `PUT /v1/devices/{user}/{device}/prekeys` (signed), `GET /v1/devices/{user}/{device}/prekey-bundle`, `POST /v1/messages`, `GET /v1/devices/{user}/{device}/messages` (signed). Auth failures are `401` with a specific `error`; map every exception explicitly; any other server/storage failure is `500` `internal_error` (logged, never the exception text). JSON via kotlinx.serialization; prekey bytes are Base64 strings. `client:core` transport errors are `SecureMessageTransportException`.
