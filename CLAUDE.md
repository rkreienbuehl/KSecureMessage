# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

KSecureMessage is an early-stage Kotlin Multiplatform scaffold for a Signal-style secure messaging library built on [Kodium](https://github.com/LivotovLabs/kodium) (which provides the X3DH and Double Ratchet primitives). It adds the messaging lifecycle and infrastructure around those primitives. It does **not** aim for wire compatibility with Signal/libsignal. `KodiumProtocolEngine` implements milestone 1 (X3DH session setup, Double Ratchet, session export/restore; tests in `core/protocol/src/commonTest`). Milestone 2 added `CiphertextMessageCodec` (versioned binary wire format for `EncryptedEnvelope.payload`, spec in `docs/wire-format.md`) and the `SecureMessageClient` send/receive path; tests in `core/protocol` and `client/core` `commonTest`. ## Commands

The Gradle wrapper (Gradle 9.6) is checked in. Tests exist in `core:protocol`, `client:core`, `storage:encryption`, `storage:rotation:core`, `storage:client:inmemory`, `storage:client:sqldelight`, `storage:server:inmemory`, `storage:server:sqldelight`, `storage:keyprovider:android`, `storage:keyprovider:apple`, `server:core` and `server:ktor`. There is no lint setup.

```bash
./gradlew build                          # everything (all KMP targets; native/iOS need macOS)
./gradlew compileKotlinJvm               # fast check of KMP modules via JVM target
./gradlew compileAndroidMain             # Android target of all client-side modules
./gradlew :server:core:compileKotlin :server:ktor:compileKotlin
./gradlew :core:protocol:jvmTest         # KMP module tests on JVM
./gradlew :core:protocol:macosArm64Test  # same tests, native
./gradlew :core:protocol:jvmTest --tests "dev.kreienbuehl.ksecuremessage.protocol.SomeTest"
./gradlew :server:core:test :server:ktor:test  # JVM-only modules use plain `test`
./gradlew :storage:server:sqldelight:test      # persistent server storage (JVM only, in-memory + file-backed SQLite)
./gradlew :storage:client:sqldelight:jvmTest :storage:client:sqldelight:macosArm64Test  # SQLite-backed tests (no JS/Wasm tests)
./gradlew :storage:rotation:core:jvmTest                       # storage key rotation state machine, fake backend
./gradlew :storage:keyprovider:android:testAndroidHostTest     # wrapped key file codec, JVM host
./gradlew :storage:keyprovider:android:connectedAndroidDeviceTest :storage:client:sqldelight:connectedAndroidDeviceTest  # needs a running emulator/device
./gradlew :storage:keyprovider:apple:macosArm64Test            # legacy keychain contract, no-fallback tests
./gradlew appleKeychainHostTest                                # data protection keychain in the signed host (macosArm64 + iosSimulatorArm64)
./gradlew iosSimulatorArm64KeychainHostTest                    # needs a booted simulator only
```

Instrumented tests (`connectedAndroidDeviceTest`) and the keychain host tasks are not part of `build`. Kotlin/Native test binaries are unsigned (macOS data protection keychain: -34018; iOS simulator runner: no keychain, -25291), so plain `macos*Test`/`ios*Test` tasks exclude every `*DataProtection*` test class; those run only in the host (`<target>KeychainHostTest`), which reports PASSED / FAILED / NOT EXECUTED. Never add a skip path that returns normally: a `DataProtection` test must fail when the keychain is unusable. macOS host signing comes from local `ksm.apple.teamId` / `ksm.apple.macosProfile` (never commit team IDs, identities or profiles). Host tasks share one lock (the simulator hosts share a bundle ID). `:storage:keyprovider:apple:<target>KeychainHostPurge` removes items an interrupted run left.

JS/Wasm test tasks (and so plain `./gradlew build`) fail with "repository 'Distributions at https://nodejs.org/dist' was added by unknown code". The cause is `RepositoriesMode.FAIL_ON_PROJECT_REPOS` in `settings.gradle.kts`. Until that is fixed, run `./gradlew build -x jsTest -x jsNodeTest -x jsBrowserTest -x wasmJsTest -x wasmJsNodeTest -x wasmJsBrowserTest`.

Configuration cache is on (`gradle.properties`). Android builds need `ANDROID_HOME` (a local SDK).

## Module layout and targets

- **Client-side / shared** (`core:model`, `core:protocol`, `storage:core`, `storage:encryption`, `storage:rotation:core`, `storage:client:inmemory`, `storage:client:sqldelight`, `storage:server:inmemory`, `storage:testing`, `client:core`, `client:ktor`): Kotlin Multiplatform with jvm, android, js, wasmJs, iOS, macOS, linuxX64, mingwX64. Exceptions: `storage:keyprovider:android` has only the android target (`androidMain`, `androidHostTest`, `androidDeviceTest`), `storage:keyprovider:apple` only iOS/macOS (`appleMain`, `macosMain`, `appleTest`, `macosTest`). Sources live in `src/commonMain/kotlin`. Android uses the AGP 9 `com.android.kotlin.multiplatform.library` plugin with a `kotlin { android { namespace/compileSdk/minSdk } }` block. The SDK levels come from `libs.versions.toml`.
- **Server** (`server:core`, `server:ktor`, `storage:server:sqldelight`): plain `kotlin.jvm` with `jvmToolchain(17)`. Sources live in `src/main/kotlin`. Do not add non-JVM targets here. The root `build.gradle.kts` sets the KMP JVM targets to Java 17 bytecode so the server can load them.
- `kotlin.mpp.applyDefaultHierarchyTemplate=false` is set, so there are no intermediate source sets (for example, no `iosMain`/`nativeMain`) unless you declare them explicitly.
- Each module's Maven group includes its parent directory (`dev.kreienbuehl.ksecuremessage.client:core`, `...storage:core`), set in the root `build.gradle.kts`. Several modules are named `core`. With a shared group, Gradle resolves `:storage:core` to itself and reports circular task dependencies, so keep coordinates unique.
- Dependency versions live only in `gradle/libs.versions.toml`.
- `storage:client:sqldelight` and `storage:keyprovider:apple` link `apple-keychain-host/ios-simulator.entitlements` into their `iosSimulatorArm64` test binaries (`-sectcreate __TEXT __entitlements`). `storage:client:sqldelight` wires custom test source sets: `sqliteTest` (shared by `jvmTest`, `nativeTest` and `androidDeviceTest`; `appleTest`/`macosTest` sit between `nativeTest` and the Apple targets), with `expect`/`actual` test drivers. JS/Wasm have no test sources there. Its linuxX64/mingwX64 test link and run tasks are skipped unless the host OS matches (they need the target's libsqlite3).
- `storage:testing` holds `ClientStorageContractTest`, `PreKeyRepositoryContractTest`, `MailboxRepositoryContractTest`, `DeviceRegistrationRepositoryContractTest`, `DeviceRecoveryRepositoryContractTest`, `DeviceAuthenticationRotationRepositoryContractTest`, `LastDeviceRecoveryRepositoryContractTest`, `RecoveryKeyLifecycleRepositoryContractTest`, `AuthenticationNonceRepositoryContractTest` and `StorageKeyProviderContractTest` (in `commonMain`, depends on kotlin-test). Every `ClientStorage` / server repository / platform `StorageKeyProvider` adapter's tests extend them.

## Architecture

Dependency direction: `core:model` ← `core:protocol` ← `storage:core` ← {`client:core`, `server:core`, `storage:client:inmemory`, `storage:server:inmemory`, `storage:server:sqldelight`, `storage:encryption` ← {`storage:rotation:core` ← `storage:client:sqldelight`, `storage:keyprovider:android`, `storage:keyprovider:apple`}}. `storage:client:*` = local client persistence, `storage:server:*` = server repository persistence, `storage:core` = the shared contracts (never duplicate them in an adapter module); `storage:encryption`, `storage:keyprovider:*` and `storage:rotation:core` are storage security infrastructure that today serves only persistent client storage. Main scopes never cross sides: no client module depends on a `storage:server:*` adapter and no server module on a `storage:client:*` adapter (only test scopes do: `client:core` tests use `InMemoryServerStorage` as fake server, `server:ktor` tests run a real client with `InMemoryClientStorage`). `storage:rotation:core` must never depend on SQLDelight or a platform module. `client:core` never depends on a storage adapter; applications choose one. The transport adapters (`client:ktor`, `server:ktor`) sit on top of those. `storage:core` depends on `core:protocol` because `SessionStore` persists `SecureSession`.

Key boundaries:

- **Kodium stays behind `ProtocolEngine`** (`core:protocol`). Public models use `ByteArray` for keys (`PreKeyBundle`) and ratchet state (`SecureSession.state`, meant to be Kodium's export/import blob). Do not leak Kodium types into model, storage, client, or server APIs. `kodium` is an `implementation` dependency on purpose.
- **Ratchet state must update atomically.** `ProtocolEngine.encrypt/decrypt` return an `updatedSession`. The client must persist it inside `ClientStorage.transaction { }` together with the crypto operation (see `SecureMessageClient`).
- **Server authentication (M12):** the device authentication key (Ed25519, 32-byte public key, 32-byte seed) is not the messaging identity key; never reuse or derive one from the other. Keys come only from `ProtocolEngine`; `initialize()` creates it with the identity, or once when `awaitsUpgradeKey()` (pre-M12 storage), and otherwise fails closed with `InconsistentStorage`; never regenerate a lost key. `initialize()` never registers; registration is explicit and verified with the key in its body (the only such endpoint); every other protected request verifies with the **registered** key, never one the request supplies. The signed input format v1 (domain `KSecureMessage-ServerAuth-v1`, vectors in `ServerRequestAuthenticationTest`) is frozen; sign the exact body bytes, never re-serialized JSON; paths come from `ServerApiPaths`, never the raw URI. Check order: present → registered → window (±5 min inclusive, injected `Clock`) → signature → nonce claim (atomic, per device, pruned by timestamp); authenticate before parsing or mutating. Protected operations need an `AuthenticatedDevice` (internal constructor). Registration never replaces a registered key; only device recovery, routine rotation and last-device recovery do. Bundle fetch and `POST /v1/messages` stay public.
- **Device recovery (M14):** recovers only `DeviceAddress → device auth public key`; never touch messaging identity, TOFU pins, sessions, prekeys, tombstones or the mailbox. Authority: another **registered** device with the same `UserId` (exact compare), never the target itself, verified with its **registered** key; the target must be registered (no bootstrap). Both proofs over one statement (target, authorizer, replacement key, timestamp ms, 16-byte nonce): authorization domain `KSecureMessage-DeviceRecovery-v1`, PoP domain `KSecureMessage-DeviceRecovery-PoP-v1`, `DeviceRecoveryId` = SHA-256 with `KSecureMessage-DeviceRecoveryId-v1`; formats, transfer encoding v1 and vectors in `DeviceRecoveryTest` are frozen; ServerAuth v1 is unchanged. Server check order: sizes → self → cross-user → authorizer registered → target registered → window (±5 min, injected `Clock`) → authorizer signature → PoP → `replaceForRecovery`. `replaceForRecovery` is one atomic step: matching `recovery_id` = already applied (no write) → CAS on target **and** authorizer key+epoch, replacement ≠ current key → prune + claim nonce under the target → key, `auth_epoch + 1`, `recovery_id`. The recovery's nonce claim joins that transaction (unlike ordinary requests); never clear target nonces on recovery (it would let a stale K1→K2 replay overwrite K3). Epochs start at 1, only grow. Client: the pending key is created only by explicit `prepareDeviceAuthenticationRecovery`, reused until completed or cancelled, sealed (record type 8, own AD type), in `SEALED_COLUMNS`/rotation; never delete the active key when recovery starts; promote pending → active in one transaction only after the server accepted it (success, "already applied", or the `resolve…` registration probe returning `204`); `initialize()` still fails closed on a lost key. Never send recovery requests inside a storage transaction. Single-device users have no recovery path by design.
- **Routine rotation (M16):** a separate protocol from recovery: never route it through the recovery endpoint, never let recovery and rotation signatures verify for each other (own domains `KSecureMessage-DeviceAuthRotation-v1` / `-PoP-v1` / `KSecureMessage-DeviceAuthRotationId-v1`). Statement v1 (address, K1, K2, expected epoch i64 ≥ 1, timestamp ms, 16-byte nonce) and vectors in `DeviceAuthenticationRotationTest` are frozen; K1 = K2 is unrepresentable. The endpoint carries no ServerAuth headers: the K1 authorization is its authentication, one nonce (the statement's), claimed under the device inside the CAS transaction (shared namespace with ServerAuth nonces); never clear nonces. Server check order: route address → registered → window (±5 min, injected `Clock`) → exact retry (stored `rotation_id` equals this statement's ID and registered key = K2: verify K1 sig with the statement's K1 and PoP, `ALREADY_APPLIED`, no write) → registered key = K1 and epoch = expected (else conflict) → K1 signature with the **registered** key → PoP → `replaceForRotation`. Storage shares one private CAS helper with `replaceForRecovery` (key+epoch compare, `Long.MAX_VALUE` → `EPOCH_EXHAUSTED`, never wrap, nonce claim, write); a recovery sets `recovery_id` and clears `rotation_id`, a rotation the reverse. The client learns the epoch only from the signed `GET …/registration`. Pending rotation key: created only by `prepareDeviceAuthenticationRotation` (needs K1), sealed record type 9 (own AD), in `SEALED_COLUMNS`/rotation, reused until completed or cancelled, never pending together with a recovery key (client and storage both refuse); K1 stays active until the server accepted; promote in one transaction after success, `ALREADY_APPLIED` or the K2 registration probe (if another instance on the same storage already promoted exactly that key, that counts as done); resolve on K1 `INVALID` for the epoch read and on `CONFLICT`/`EXPIRED`/`REPLAY`; never promote K2 because K1 vanished; never delete the pending key automatically. Rotation steps of one client share `deviceAuthenticationMutex` (public functions lock, `…Locked` variants do the work). Never send rotation requests inside a storage transaction.
- **Rotation policy and key age (M17):** the key's installation time is server-owned metadata: set only by first registration, recovery and rotation, with the server clock's `now` (ms), in the same atomic step as key and epoch; never from a client-supplied timestamp; never changed by a registration retry/probe, an exact retry or a rejected transition. The client never persists it (no client schema change) and never caches the status: every evaluation reads the signed `GET …/registration`. Age = client clock − installation time, clamped at zero; due iff `age >= maxKeyAge`; `maxKeyAge > 0`, `INFINITE` = never; no default policy. Evaluation never rotates or creates a key. `rotateDeviceAuthenticationKeyIfNeeded`: pending recovery → `RecoveryInProgress` (nothing sent); pending rotation → complete it (M16 resolution) → `ResumedPendingRotation`; else status → `NotNeeded` or M16 rotation → `Rotated`. Nothing calls these implicitly (not `initialize`, `send`, `receive`, `publishPreKeys`, registration, recovery); no scheduler, worker or server-triggered rotation; the server exposes metadata, never "due". ServerAuth authenticates the request, not the response. Server storage: repositories take the time as a parameter and read no clock, except `SqlDelightServerStorage.open`, which stamps `auth_key_installed_at IS NULL` rows (migrated by `3.sqm`) once with its `clock`; never rewrite a stamped time; a `NULL` after open fails closed.
- **Last-device recovery (M18):** recovers only `DeviceAddress → device auth public key` when neither another device (M14) nor the current key (M16) can; never touch messaging identity, pins, verification, sessions, prekeys, tombstones, mailbox, pending/processed messages or storage keys. The recovery key is an asymmetric Ed25519 key per `UserId`: the server stores only the public key (never a seed, never a symmetric verifier); the client never stores the seed (the application keeps it offline, `encode`/`decode` strict canonical Base64url, redacted `toString`); keys only from `ProtocolEngine`. Registration: ServerAuth-signed by a registered device of the same user plus the key's own PoP bound to the `UserId`; absent → store (epoch 1), revoked → store at epoch + 1 (M19), same active → idempotent, different active → `LastDeviceRecoveryKeyException.Conflict`; registration never replaces an active key (only an M19 rotation does); never register implicitly. Challenge: public endpoint, server `SecureRandom` 16-byte ID + 32-byte nonce, current epoch, expiry = server now + 5 min (inclusive), stored with the key it was issued for (never returned); one per device, the valid one is returned again (never let a request invalidate another's challenge), replaced only when expired or the registration changed; pruned in challenge issue and replacement transactions only (no scheduler). Statement v1 (target, recovery public key, challenge ID, nonce, epoch, expiry, K2 ≠ recovery key) and vectors in `LastDeviceRecoveryTest` are frozen; K1 is not in it (the challenge row carries it). Server check order: route target → recovery key registered (active) and equal to the statement's → target registered → exact retry (stored `last_device_recovery_id` = ID and registered key = K2, both proofs) → challenge matches (ID, nonce, epoch, expiry, recovery key epoch = current, M19) → not expired → key+epoch = the challenge's → recovery signature with the **registered** recovery key → PoP → `replaceForLastDeviceRecovery`. Storage uses the shared CAS helper with the challenge deletion as its claim step (no `authentication_nonce` row, never clear nonces); sets `last_device_recovery_id` and clears `recovery_id`/`rotation_id` (recovery and rotation clear it in turn; at most one of the three is set); `installedAt` = server now. Client: pending key only via `prepareLastDeviceRecovery` (needs the identity), sealed record type 10, in `SEALED_COLUMNS`/rotation, never pending together with a recovery or rotation key (client and storage refuse; `LastDeviceRecoveryInProgress`); all steps under `deviceAuthenticationMutex`; promote in one transaction after success, already applied, or the K2 registration probe (after `CONFLICT`/`EXPIRED`/`CHALLENGE_INVALID`); never send inside a storage transaction; `initialize()` still fails closed until promotion.
- **Recovery key lifecycle (M19):** changes only the per-user recovery key state (`last_device_recovery_key_state`), the user's challenges and one nonce; never device registrations/epochs/installation times, messaging identity, pins, verification, sessions, prekeys, tombstones, mailbox or messages. Two authorities always: ServerAuth v1 by a registered device of the user (authenticated before parsing) **and** the current recovery key's signature over a statement naming that device (the route's device is the authorizer; the body never carries it); a rotation's new key proves possession under its own domain. Never add a device-only or recovery-key-only path, and never let a lost offline key be replaced by a device (documented decision). Statement formats v1 (user, authorizer user + device, current key, [new key ≠ current,] expected recovery key epoch ≥ 1, timestamp ms, 16-byte nonce) and vectors in `RecoveryKeyLifecycleTest` are frozen; domains never shared. State: no row = UNCONFIGURED, 1 = ACTIVE (key + `installed_at`), 2 = REVOKED (no key); recovery key epoch 1 at first registration, + 1 per rotation, revocation and registration after revocation, never reset, never wraps (`Long.MAX_VALUE` → `EPOCH_EXHAUSTED`), independent of `auth_epoch`; `installedAt`/`transitionedAt` only from the server clock; at most one of `rotation_id`/`revocation_id`, registration clears both. Service order (rotation): authorizer = authenticated device → state exists → exact retry (`rotation_id` = ID and active key = new key; both proofs with the statement's keys; before the window, no write) → active → window ±5 min → key+epoch = statement's → R1 signature with the **registered** key → new-key PoP → `rotateRecoveryKey` (on CONFLICT re-check exact retry); revocation the same with one proof (exact retry: revoked with this `revocation_id`). Storage: one atomic step with a shared private CAS helper per adapter: exact retry → key/epoch/state and the authorizer's registration (`AuthenticatedDevice.registrationState`, key+epoch) unchanged, new ≠ current (else CONFLICT) → exhaustion → nonce prune + claim under the authorizer in the `authentication_nonce` namespace (REPLAY) → guarded UPDATE (`public_key IS expected`) → delete **every** challenge of the user. Challenges carry `recovery_key_epoch`; issue/replace/consume compare it with the current epoch; a revoked user gets NotConfigured. Client: `lastDeviceRecoveryKeyStatus`/`rotateLastDeviceRecoveryKey(current, new)`/`revokeLastDeviceRecoveryKey(current)` under `deviceAuthenticationMutex`, status first (new key active → `ALREADY_ACTIVE`, revoked → `ALREADY_REVOKED`, nothing sent), never persists R1 or R2, never called implicitly; the app must back up the new key before rotating. The signed status returns the active public key (needed for lost-response resolution); never return it on public endpoints.
- **Server is a blind relay.** `SecureMessageServer` only stores public prekeys and queues opaque `EncryptedEnvelope`s per recipient `DeviceAddress` (`drain` removes the envelopes it returns). It must never decrypt payloads or hold client session secrets.
- **Server prekeys:** `PreKeyRepository` (`storage:core`) keeps per device an identity key, the current signed prekey, available one-time prekeys and consumed-ID tombstones. `publish` is atomic and idempotent; conflicts throw `PreKeyPublicationException` and change nothing. `consumePreKeyBundle` removes and tombstones the lowest-ID one-time prekey in one atomic step, so no one-time prekey is handed out twice, even if the client uploads it again. Server consumption is not client consumption: the client deletes its private one-time prekey only when it accepts the `PreKeyMessage`. `PreKeyFormat` (`core:protocol`) checks publication sizes without Kodium.
- **Message reliability (M8):** two layers in `SecureMessageClient`. Public = reliability layer (`send`, `decrypt`, `retryPendingMessages`, `pendingMessages`, since M20 `pendingReceivedMessages`, `commitReceivedMessage`, `pruneProcessedMessages`, since M21 `discardReceivedMessage`, `pendingReceivedMessageCount`, since M22 paginated `pendingMessages`, `pendingMessageCount`, `abandonPendingMessage`); `internal` `encryptRaw`/`sendRaw`/`decryptRaw` = session layer with M1–M7 semantics, used by it and by the M1–M7 tests (tests of session behavior use the raw layer; other modules' tests must use the public API and expect ACK envelopes in mailboxes). Every ratchet plaintext is a `SecurePayloadCodec` frame; no fallback for raw plaintext, never use `EncryptedEnvelope.protocolVersion` to detect it; frame v1 vectors are frozen. `send`: pending store + encryption + session in one transaction, hand-off after; `MessageNotSent` after a failed hand-off, never rewind the session. Pending is removed only by an ACK from that recipient or an explicit `abandonPendingMessage` (M22), never on transport success, never automatically. Abandon is local: never send anything for it (no new frame type, no fetch), never touch the session, sequences or receiver-side state, keep it under `sendMutex` and one transaction, no tombstone; outbound enumeration is cursor-only like inbound. `decrypt` (M20): in the receive transaction processed → `AlreadyCommitted` + ACK, pending → the same `Delivery` again (no second row, no ACK), else store pending inbound → `Delivery`, no ACK; a different body for the same (sender, ID) throws `LogicalMessageConflict` inside the transaction (compare pending body constant-time, committed via digest; legacy `NULL` digest counts as committed). `commitReceivedMessage`: one transaction removes pending and writes processed (digest, `committedAt` from the injected clock), then ACK outside it; ACK failure never rolls back the commit; second commit = `ALREADY_COMMITTED` + ACK again; unknown = `ReceivedMessageNotPending`. ACKs go on the existing session only, under `sendMutex`, failures give `ackSent = false` (rethrow `CancellationException`); never ACK before the commit, an ACK, or anything that failed (collision, stale, identity, expired SPK, malformed frame, conflict). ACK = the receiving application durably finalized (committed or discarded, M21); never claim exactly once. Retry re-encrypts the stored frame fresh, same logical ID, new envelope ID, in sequence order, stops at the first hand-off failure. Pending frames are plaintext in the store API (sealed by persistent adapters). Processed IDs are pruned only by explicit `pruneProcessedMessages` (`finalizedAt <= now - maxAge`, committed and discarded alike, maxAge rounded up to ms, `INFINITE` = none, no default, never implicit); never prune, expire or auto-discard pending inbound; `initialize()` stamps legacy `committed_at IS NULL` once, never rewrites. Discard (M21): same transaction shape as commit (pending removed, plaintext gone, tombstone with DISCARDED + digest (record type 12) + time + reason), ACK after the commit; a terminal outcome is never replaced (storage throws, commit/discard report `ALREADY_*`); unknown ID → `ReceivedMessageNotPending`, no tombstone; the discard reason is a closed enum stored as plaintext code, never sent; no bulk discard, no dead-letter plaintext, no sender-visible rejection. Pending enumeration is cursor-only (`sequence > afterSequence`, ascending, `1..PendingReceivedPage.MAX_SIZE`), never OFFSET and never an unbounded list; unknown finalization/reason codes fail closed (`IllegalStateException`), never read as absent.
- **Wire format:** `CiphertextMessageCodec` (`core:protocol`, no Kodium imports) owns the payload bytes; version-1 vectors in `CiphertextMessageCodecTest` are frozen. `EncryptedEnvelope.protocolVersion` versions only the envelope metadata. Protocol info strings live in `ProtocolConstants` and must never change.
- **Client storage:** `ClientStorage` has `identity`, `remoteIdentities` (TOFU pins), `sessions`, `sessionInitiations` (retired initiation IDs, each with an optional local signed prekey ID for pruning), `preKeys` (local private prekeys plus signed prekey `createdAt`/`replacedAt`), `pendingOutbound` (recipient + logical ID → never-reused sequence + encoded frame), `pendingInbound` (sender + logical ID → never-reused sequence, `receivedAt`, frame; M20) and `processedInbound` (sender + logical ID → digest + `committedAt`, both `null` for legacy rows). `transaction` must be atomic (rollback on throw), nested calls join the running transaction, and blocks must not do network I/O or switch threads. Accepting a `PreKeyMessage`, storing the session and removing the consumed one-time prekey happen in one `transaction`.
- **Local key lifecycle:** keys are created only by `ProtocolEngine`, never by storage. `PreKeyManager` allocates prekey IDs from persisted high-water marks (never reused, no wraparound; `PreKeyIdsExhausted`). Operations before `initialize()` throw `SecureMessageClientException.NotInitialized`. An existing identity is never replaced.
- **Signed prekey lifecycle (M7):** current → (rotate) grace → (grace over) physically deleted. Never delete at rotation. `initialize()` does all maintenance in one transaction (stamp pre-M7 keys, age rotation, expiry, pruning); it never publishes. Acceptance refuses a key past its grace period even before deletion (`ExpiredSignedPreKey`); never-issued IDs stay `InvalidMessage`. Negative ages are never due; deleted keys never come back. Only use the injected `Clock`, never `Clock.System` directly. Prune a retired initiation only by its **local** signed prekey ID and only after that key is deleted; `null` entries (own initiations, pre-M7) are kept. Established sessions never depend on the signed prekey.
- **Session lifecycle (M6):** every session stores the `SessionInitiationId` that created it (SHA-256, domain `KSecureMessage-SessionInitiation-v1`; vectors in `SessionInitiationIdTest` are frozen). A `PreKeyMessage` goes through `SecureMessageClient.receivePreKeyMessage`: identity check → same initiation (decrypt) → retired (`StaleSessionInitiation`) → accept, collision (smaller ID wins, the loser is authenticated, retired, `SessionCollision`, OTPK kept) or replacement (session + retire old origin + OTPK removal in one transaction). Header fields are authenticated only by `acceptSession`; never record an origin from `decrypt`. Sessions without a pin are never replaced. Never order initiations by "age": the ID order is only a tie-break.
- **Remote identity trust (TOFU):** pins are per `DeviceAddress`, written only after the protocol accepted the key (`initiateSession` / successful decrypt) and in the same transaction as the session (and OTPK removal). Check before crypto, pin after. Message and bundle processing never replace a pin; a different key throws `IdentityChanged` and changes nothing. Never derive a pin from the envelope sender address. SQLDelight schema changes need a new `.sqm` migration (current version 15) and a frozen schema fixture (`Version1Schema` … `Version14Schema`) for migration tests. `LegacyPlaintextMigration` rebuilds `pending_outbound_message`, so it must recreate that table's indexes.
- **Identity verification (M15):** messaging identity only; never mix in device-auth, storage, prekey or session keys, and never touch verification from device recovery. Safety number v1 (domain, canonical order by address encoding, 12×5-digit display from 20-bit chunks, payload v1) is frozen. Derive only from the local identity and the **pinned** key; never fetch a bundle for it. Comparing or decoding never changes trust; `markRemoteIdentityVerified` takes the `SafetyNumber` the user compared and fails if the pin changed. New and replaced pins are `UNVERIFIED`; never carry `VERIFIED` to another key. Only `acceptRemoteIdentityChange` replaces a pin: under `sendMutex`, one transaction, CAS on the previous key, retire + remove the old session, install exactly the presented key of the `RemoteIdentityChange` (never a freshly fetched one); keep pending outbound and processed inbound. Never auto-accept. `remote_identity` stays unsealed; unknown verification codes fail closed. A change to a sealed table also needs a Kotlin data migration like `LegacyPlaintextMigration`, because SQL cannot encrypt.
- **Storage encryption (M9):** `SqlDelightClientStorage` seals key pairs (whole identity/device-auth/SPK/OTPK records; device authentication key = record type 7, M12), session state, pending frames (outbound and, M20, inbound) and processed digests with `ClientRecordCipher` (`storage:encryption`); adapters never do crypto, AD or formats themselves. Only `AesGcm.kt` imports cryptography-kotlin; Kodium is not used for storage. AD = record header + domain `KSecureMessage-Storage-v1` + record type ID + length-prefixed row key fields; record type IDs (1–12; 8 = pending device recovery key, M14; 9 = pending device authentication rotation key, M16; 10 = pending last-device recovery key, M18; 11 = pending inbound frame, 12 = processed inbound digest, M20, also for discarded tombstones since M21), domain and record format v1 (vectors in `StorageCipherTest`) are frozen. Nonces are always fresh random 96-bit. A record that fails to open throws `StorageEncryptionException`, never returns `null`; existence checks (identity already stored, pending duplicate) must not open records. No plaintext mode, no trial decryption: the `storage_encryption.format` row is authoritative (0 = M8 plaintext, migrated by `open` in one transaction; 1 = encrypted). Key providers are called outside transactions; `open` never creates a key for a database with a bound key. It is record-level encryption, not database encryption: metadata, row deletion and rollback are unprotected, and pre-M9 plaintext may remain in SQLite pages. `InMemoryClientStorage` does not encrypt. The pre-v6 sealed-table DDL exists twice (`ClientState.sq`, `LegacyPlaintextMigration.kt`; tables added later, like `device_authentication_key`, `device_authentication_recovery_key`, `device_authentication_rotation_key` and `device_authentication_last_device_recovery_key`, only in `ClientState.sq` and their `.sqm`); `SqlDelightMigrationTest.migratedSchemaEqualsNewSchema` checks they match.
- **Platform key providers (M10):** they only persist the unchanged 32-byte M9 key (`StorageEncryptionKey.generate`), never derive it. Create only when the provider has **no state**; state present but unreadable (missing Keystore alias, damaged file/item, wrong size, any OSStatus except not-found) is `KeyUnavailable`, never a new key, and never overwrites anything. Return a created key only after it was persisted and read back. `key(id)` never creates; `loadOrCreateKey()` refuses a namespace with several keys. `createKey(id)` returns an existing key unchanged or creates, persists and reads back a new one (needs a provisioned provider); `removeKey(id)` removes exactly one key and never the last one. No reset or delete-all API in production code; tests clean up with test-only helpers and random namespaces. Android: raw key never written; alias, file name, file format v1 and wrap AD are documented and frozen; files go through temp file + `ATOMIC_MOVE`; process mutex + file lock. Apple: item data is exactly the 32 raw bytes; service/account naming, `AfterFirstUnlockThisDeviceOnly`, non-synchronizable and data protection keychain are the defaults; never fall back to the legacy macOS keychain automatically. First key ID is 1.
- **Storage key rotation (M11):** not signed prekey rotation. The state machine (step order, allocation rule, provider calls and read-back, zero-reference rule, `removeKey == false` accepted only in RETIRING) lives only in `StorageKeyRotationManager` (`storage:rotation:core`); never duplicate phase logic in a backend. A backend (`SqlDelightStorageKeyRotationBackend`) owns persistence, transactions, phase encoding, key checks, batches and the scan; each transition is one atomic compare-and-set, and `markRetiring` runs the scan and the manager's check in the committing transaction. Generic state validation is `StorageKeyRotationState.of`. The database owns rotation state (`storage_encryption`: `key_id` current, `highest_key_id`, `rotation_phase` 0 STABLE / 1 PREPARING / 2 MIGRATING / 3 RETIRING, `next_key_id`, `retiring_key_id`, `retiring_key_check`); providers only hold keys; key IDs come from the high-water mark, never reused, no wraparound (`KeyIdsExhausted`). Order: allocate ID (commit) → `createKey` + read back → activate (commit) → batches → proof tx (clear retiring check, scan) → re-scan → `removeKey` → STABLE. Never let the database name a key before the provider persisted it; never remove a key before the scan committed RETIRING; `removeKey` returning `false` is fine only in RETIRING. New records always use the current key; reads pick the key by record header. Re-encryption `UPDATE`s only the sealed column, same AD, fresh nonce; one transaction per batch, failures roll back only that batch and keep MIGRATING. `SEALED_COLUMNS` must list every sealed column (checked against the schema by `sealedColumnsCoverEverySealedValueInTheSchema`). `open` loads exactly the keys the phase needs, verifies each key check with a single-key cipher, never advances or rolls back a rotation. Every top-level transaction checks the key state (stale instance → `KeyUnavailable`). No scheduler; orphan provider keys are never deleted.
- **Delivery order:** convergence needs, per (sender, recipient) pair, every `PreKeyMessage` processed before later envelopes of that sender (`docs/transport-ordering.md`). Keep every encrypt+hand-off (`send`, retries, ACKs) under `sendMutex` (never inside a storage transaction), and any `MailboxRepository` per-pair FIFO and exactly-once per drain. Order across senders is not promised; do not add sequence numbers to `EncryptedEnvelope`.
- **Persistent server storage (M13):** `SqlDelightServerStorage` takes a caller-supplied `SqlDriver`; never create, configure or close a driver in the adapter, and never expose a concrete driver type. SQLite dialect and synchronous drivers only; never claim other databases (a PostgreSQL adapter would be its own module). Main scope depends only on `storage:core` + SQLDelight runtime (never client storage, encryption, key providers or rotation). Every repository call is one transaction under the instance mutex; one instance per database. Never `INSERT OR REPLACE`; uniqueness lives in primary keys. The nonce claim (prune + insert) is its own transaction, never joined with the protected operation. Publication, OTPK hand-out (delete + tombstone) and drain (select + delete) are each one transaction; `enqueue` returns after commit. `mailbox_message.sequence` is `AUTOINCREMENT` (never reused). Schema changes need a server-own `.sqm` (no client numbering; current server schema version 6 via `1.sqm` … `5.sqm`, `server_storage.format` = 6, frozen fixtures `ServerVersion1Schema` … `ServerVersion5Schema`); `open` never migrates a schema, refuses formats 1–5, and only stamps legacy key installation times (M17). `server:ktor` main never depends on SQLDelight (tests may). Restart tests must close the driver and reopen the same file.
- **HTTP contract** (API v1) is defined twice and must stay in sync: `client:ktor` (`KtorSecureMessageTransport`, `HttpDtos.kt`, `AuthHeaders`) and `server:ktor` (`KSecureMessageRoutes`, `HttpDtos.kt`, `AuthHeaders`); `server:ktor` tests run the client adapter against the routes. Routes: `PUT /v1/devices/{user}/{device}/registration` (signed), `PUT /v1/devices/{user}/{device}/registration/recovery` (both recovery signatures in the JSON body, no auth headers), `PUT /v1/devices/{user}/{device}/registration/rotation` (K1 authorization + K2 PoP in the body, no auth headers), `GET /v1/devices/{user}/{device}/registration` (signed, returns the auth epoch and the key installation time), `PUT /v1/devices/{user}/{device}/last-device-recovery/key` (signed), `GET /v1/devices/{user}/{device}/last-device-recovery/key` (signed, recovery key status), `PUT /v1/devices/{user}/{device}/last-device-recovery/key/rotation` and `…/key/revocation` (signed, current recovery key signature [+ new-key PoP] in the body), `POST /v1/devices/{user}/{device}/last-device-recovery/challenge` (public), `PUT /v1/devices/{user}/{device}/last-device-recovery` (recovery signature + PoP in the body, no auth headers), `PUT /v1/devices/{user}/{device}/prekeys` (signed), `GET /v1/devices/{user}/{device}/prekey-bundle`, `POST /v1/messages`, `GET /v1/devices/{user}/{device}/messages` (signed). Auth failures are `401` with a specific `error`; map every exception explicitly; any other server/storage failure is `500` `internal_error` (logged, never the exception text). JSON via kotlinx.serialization; prekey bytes are Base64 strings. `client:core` transport errors are `SecureMessageTransportException`.
